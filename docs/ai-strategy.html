Current State — Direct Gemini API

Key Concept · Phase 1 Quick Win

Confidence-Gated Routing

The Gemini model already returns a confidence field with every score: high, medium, or low. We are currently storing this but not acting on it. Confidence-gated routing means using the model's own uncertainty signal to decide how much to trust its output — without changing the model at all.

The Core Idea

Not all AI scores carry equal weight. A high-confidence score of 85 means "I can clearly see this photo meets the spec." A low-confidence score of 72 means "the image is blurry / I'm not sure what I'm looking at — this number is a rough guess." Treating these identically risks both over-trusting wrong scores and wasting reviewer time on obviously good photos.

Why This Matters

The Problem Without Routing

A photo with confidence=low, score=71 looks like a passing score. A reviewer may rubber-stamp it. But the model was telling us it wasn't sure — the photo may be blurry, taken at the wrong angle, or showing something ambiguous. We silently trust a guess.

The Outcome With Routing

Low-confidence photos surface with a visual "⚠ AI Uncertain" badge. The reviewer is primed to look carefully rather than rely on the score. This catches real defects that would otherwise pass, and costs nothing — the confidence data is already there.

Implementation Plan

This is entirely a backend query + UI change. No model changes. No infrastructure. Estimated effort: 1–2 days.

Step 1 — Review Queue Ordering (Backend, ~2h)

Modify the review page query to sort confidence='low' photos to the top of the pending queue.

-- In the review queue SQL query SELECT ps.*, ai.score, ai.confidence, ai.summary FROM photo_submissions ps LEFT JOIN photo_ai_scores ai ON ai.photo_submission_id = ps.id WHERE ps.status = 'pending' ORDER BY CASE ai.confidence WHEN 'low' THEN 1 -- surface first WHEN 'medium' THEN 2 WHEN 'high' THEN 3 ELSE 2 END, ps.submitted_at DESC

Step 2 — UI Badge & Visual Alert (Frontend, ~3h)

On the review page, when confidence === 'low', show a prominent warning alongside the AI score badge.

// Review page — AI score badge component {ai.confidence === 'low' && ( <div className="rounded-lg border border-red-200 bg-red-50 p-3"> <WarningIcon /> <span className="text-red-700 font-semibold text-sm"> AI Uncertain — Review Carefully </span> <p className="text-red-600 text-xs mt-1"> Image quality or content prevented confident scoring. Do not rely on the AI score — use your own judgement. </p> </div> )}

Step 3 — Accuracy Dashboard Metric (Backend + UI, ~4h)

Track how often humans override AI per confidence level. This validates that routing is working — low-confidence scores should have a higher override rate.

-- Accuracy dashboard query SELECT ai.confidence, COUNT(*) as total, SUM(CASE WHEN (ai.score >= 70 AND ps.status = 'approved') OR (ai.score < 50 AND ps.status = 'nc') THEN 1 ELSE 0 END) as ai_agreed, ROUND(100.0 * SUM(...) / COUNT(*), 1) as agreement_pct FROM photo_ai_scores ai JOIN photo_submissions ps ON ps.id = ai.photo_submission_id WHERE ps.status IN ('approved', 'nc', 'qc_required') GROUP BY ai.confidence

Expected result: agreement_pct for 'high' ≫ 'medium' ≫ 'low'. If not, the confidence signal itself needs calibration.

Optional Step 4 — Anchoring Bias Prevention (Advanced)

When confidence='low', hide the numeric AI score entirely and show only "⚠ AI Uncertain — score hidden." Research shows that displaying an uncertain score causes reviewers to anchor to it even when told to ignore it. Hiding it produces more independent human decisions, which are higher-quality training labels for future model training.

💡
Dual value: Confidence routing immediately improves review quality (less rubber-stamping of uncertain scores). Simultaneously, photos where the model says low confidence are your highest-value training examples for future model improvement — the model is showing you exactly where it needs more domain knowledge.

The Classifier: CLIP-Based (Recommended)

CLIP (Contrastive Language–Image Pretraining) is a model trained on 400 million image-text pairs that understands both visual content and natural language descriptions together. Unlike a plain image classifier, it understands that a photo labeled "cable tray inspection" should look different from one labeled "duct sealing checkpoint." This matters because your checkpoints are diverse.

Option A — Image-Only (MobileNet)

  • → ~4M parameters, runs on CPU in <100ms
  • → Training data: 1,000–3,000 labeled images
  • ✕ Does not understand checkpoint spec text
  • ✕ Different checkpoint types need separate models
  • ✓ Simplest to deploy and maintain
RECOMMENDED

Option B — CLIP-Based (Vision + Language)

  • → ~150M parameters, runs on CPU in ~150ms
  • → Training data: 2,000–5,000 image-spec pairs
  • ✓ Understands checkpoint name + photo together
  • ✓ One model handles all checkpoint types
  • ✓ Transfers domain knowledge from existing CLIP base

Fine-Tuning: What It Actually Means

📘
Fine-tuning ≠ training from scratch. You start with a model that already understands what images and text look like (trained on the internet), then continue training it on your domain data for a few hours. Think of it as onboarding a senior engineer to your specific project — you're not teaching them programming fundamentals, you're giving them domain orientation.

Training Pipeline

# Phase 2 Training Pipeline (one-time setup, runs on GPU) 1. Export labeled dataset: photo_s3_key + checkpoint_id + human_outcome → CSV 2. Download images from S3 → local training set 3. Fine-tune CLIP on your domain: python train_clip.py \ --base-model openai/clip-vit-base-patch32 \ --dataset ./data/labeled_photos.csv \ --epochs 20 \ --output ./models/ce_df_clip_v1.pt # ~4–8 hours on single A100 GPU (one-time) # Can use Google Colab Pro ($50/mo) or RunPod (~$1–2/GPU-hour) 4. Shadow mode: run in parallel with Gemini for 2–4 weeks # Log both scores. Do NOT route traffic yet. Measure agreement. 5. If agreement > 92%, switch routing: confidence >= 0.85 → local score only confidence < 0.85 → Gemini API

Phase 3 · 24 – 36 Months

Custom Domain Model — Fine-Tuned Vision Language Model

Replace Gemini entirely (or nearly) with a self-hosted Vision Language Model (VLM) fine-tuned specifically on your fiber infrastructure domain. At sufficient data volume, a 7B parameter domain-specialized model outperforms a general-purpose 100B+ parameter model on your specific task.

What is a VLM (Vision Language Model)?

A VLM is a neural network that understands both images and text together — like Gemini, but open-source and self-hostable. Modern 7B VLMs (7 billion neural network parameters) run on a single consumer GPU after quantization and match GPT-4V quality on domain-specific tasks when fine-tuned.

The Key Technologies Explained

Quantization

Reduces model precision from 32-bit floats to 4-bit integers. A 7B model normally requires 28GB VRAM; quantized to 4-bit it needs ~4–6GB — runs on a consumer RTX 4080. Accuracy loss: ~2–5%. Speed improvement: 4–8x. This is what makes local deployment economically viable.

QLoRA (Fine-tuning Method)

Instead of updating all 7 billion parameters (massively expensive), you add small "adapter" layers (~10M parameters) and train only those on a quantized model. The base model's knowledge is preserved; you add domain specialization on top. Training on 5,000 photos: ~4–8 hours on one RTX 4090.

# Fine-tuning a 7B VLM with QLoRA (simplified) # Runs on a single RTX 4090 (24GB VRAM) — ~$0.50/hr on RunPod python train_vlm.py \ --model "Qwen/Qwen2-VL-7B-Instruct" \ --dataset "./data/ce_df_5000_labeled.json" \ --technique "qlora" \ # quantized LoRA adapters --lora-rank 16 \ # size of adapter layers --epochs 3 \ # 3 passes over your dataset --batch-size 4 \ --output "./models/ce_df_vlm_v1" # Result: base model + LoRA adapter (stored separately) # To roll back: just delete the adapter, base model is unchanged

Ongoing MLOps Requirements

MLOps is the set of practices that keep a deployed ML model healthy over time — analogous to DevOps for software, but with additional concerns around data and model drift.

Model Registry

Track model versions, training data snapshots, accuracy metrics. Roll back to previous version if a new deployment underperforms. Tools: MLflow, Weights & Biases (both open-source options available).

Evaluation Harness

Before every deployment, run the new model against a held-out test set (photos never seen during training). Must not regress on accuracy vs previous version. This is your safety gate.

Distribution Drift Monitoring

If score distribution suddenly shifts — e.g., all photos scoring 90+ — something is wrong. Could be: new checkpoint type, different camera, seasonal lighting change, or model degradation. Monitor score distribution weekly.

Retraining Cadence

Quarterly minimum. As new checkpoint types are added or field conditions change, the model's training distribution shifts. Regular retraining on the latest labeled data keeps the model current.

Leadership Q&A Prep

Anticipated Hard Questions

Q Why not just keep using Gemini forever? It's working fine.
It may be the right answer for 2–3 years — and we're not proposing to change anything immediately. The point of this plan is to preserve our options. Collecting the labeled dataset today costs nothing extra, and it's the one thing we cannot recover retroactively if we wait. The investment triggers are all pull-based: we only move to the next phase when a specific cost or accuracy threshold is crossed. We're not over-investing in ML before we have data.
Q What's the ROI on building our own model?
At 100K photos/month, Phase 3 saves roughly $150–250/month over Gemini. The one-time build cost of $15,000–25,000 has a 5–10 year payback on cost alone. The actual case is not cost — it's three things: (1) accuracy improvement from domain specialization — a model trained on 5,000 of our specific fiber inspection photos will outperform a general-purpose model; (2) latency — local inference is 10–15x faster, enabling real-time feedback during capture; (3) compliance — photos stay within our infrastructure, not Google's.
Q How do we measure accuracy? How do we know if AI is doing a good job?
We define accuracy as AI–Human Agreement Rate: when the AI scores ≥70 and the human approves, that's agreement; when AI scores <50 and human rejects, that's agreement. We track three metrics: Precision (of photos AI calls pass, what % do humans agree), Recall (of photos humans approve, what % does AI correctly pass), and F1 (harmonic mean of both). These are tracked per checkpoint type, not just overall — so we know which checkpoint types the AI handles well vs. poorly.
Q What if the custom model is wrong and we don't catch it?
Three safeguards: First, before any custom model goes to production, it must pass a held-out test of 500+ photos it has never seen, with human ground truth. If accuracy regresses vs. the previous version, the deployment is blocked. Second, for any prediction where the model's confidence is below threshold, we always route to Gemini as fallback — so we have a safety net. Third, we run distribution monitoring: if the mean score for a checkpoint shifts by more than 5 points week-over-week, an alert fires and someone investigates before the shift affects real decisions.
Q How long does training a model take? I thought AI training takes weeks.
That's training from scratch, which we're not doing. Fine-tuning using QLoRA on a 7 billion parameter model with 5,000 examples takes approximately 4–8 hours on a single A100 GPU. We don't own that GPU — we rent it for $1–2/hour for those 8 hours, then stop. The result is a set of adapter files (~100MB) that we keep. The bottleneck is dataset preparation and validation, not compute time.
Q Do we need to hire an ML team?
For Phase 1: no new hires. For Phase 2: one contract ML engineer for 4–6 weeks to build the fine-tuning pipeline and integration. After that, our existing backend developers can maintain the inference service — it's a REST API call, not fundamentally different from calling Gemini. For Phase 3+: 0.5 FTE equivalent, which can be a combination of a part-time contract ML engineer plus our existing team handling the operational side. We are applying standard, well-documented techniques using open-source tooling — not building a research organization.
Q What about data privacy? Are our infrastructure photos being used to train Google's models?
Under Google's enterprise API terms, your data is not used to train their models. However, photos do transit Google's servers — currently likely US/EU data centers. Under India's Digital Personal Data Protection Act (DPDP Act, 2023) and potential future sector-specific telecom regulations, infrastructure survey photos may eventually need to remain within Indian borders. Phase 3 self-hosted on AWS ap-south-1 (Mumbai) or Jio Cloud resolves this completely. We should monitor the regulatory situation but do not need to act immediately — the Phase 1–2 work can proceed regardless of how the regulation evolves.
Q Can we use free/open-source models right now instead of paying for Gemini?
Yes, technically. But without fine-tuning on our domain, open-source 7B models will perform worse than Gemini on our specific infrastructure photos — Gemini 2.0 Flash is genuinely excellent on out-of-the-box industrial vision tasks. The open-source advantage materializes only after fine-tuning on domain-specific data. Using an untuned open-source model to cut costs today would sacrifice accuracy. The right answer is: use Gemini now, collect data, then fine-tune open-source when we have sufficient labeled examples.
